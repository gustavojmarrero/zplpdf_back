# BE08 / BE09: Drive y PrintNode

Prefijo /api, Firebase bearer en todas las rutas; UID siempre del guard. Flags servidor folder_automation/direct_print. Módulos FolderAutomationModule y DirectPrintModule; root integra AppModule/scheduler OIDC. Sin despliegue ni impresión real durante desarrollo.

FE05: POST /integrations/drive/oauth/start {} -> {authorizationUrl,stateExpiresAt}; redirección registrada al frontend, que envía POST /integrations/drive/oauth/complete {state,code}. State de un uso vinculado a cuenta, PKCE S256, expiración diez minutos. Config GOOGLE_DRIVE_CLIENT_ID/SECRET/REDIRECT_URI; cifrado AES-GCM PUBLIC_API_ENCRYPTION_KEY (base64 32 bytes). GET /integrations/drive/connections; PATCH /connections/:id {expectedVersion,inputFolderId,outputFolderId,labelSize,recipeVersion,enabled}; POST /connections/:id/disconnect {expectedVersion}; GET /connections/:id/runs; POST /runs/:id/retry {}. IDs opacos, jamás identidad por filename. Input ZPL (text/plain o application/octet-stream), carpeta salida diferente, acceso explícito a carpetas, exclusión de outputs propios. Jobs guardan revisión exacta y snapshot de receta. Ledger durable/cursor paginado, solo output PDF confirmado produce folder_run_succeeded; escaneo vacío no es uso.

FE06: POST /print/connections {apiKey} verifica cuenta PrintNode y cifra secreto; GET /print/connections; DELETE /print/connections/:id; GET /print/connections/:id/printers. POST /print/jobs con Idempotency-Key y {connectionId,printerId,conversionId}; fuente exclusivamente conversión PDF completada propia, nunca URL de cliente. GET /print/jobs/:id; POST /print/jobs/:id/reprint {confirm:true} + nueva Idempotency-Key; POST /print/jobs/:id/confirm {printed:true}. Reprint crea operación nueva vinculada a original, nunca retry automático de unknown. Estados queued/sent/acknowledged/failed/unknown; freshness de cliente separado. Acknowledged significa llegada a cola del SO, nunca impresión física. Confirmación manual queda identificada como tal.

Selección: PrintNode dispone de API y cliente Windows; cada usuario aporta su propia cuenta/key. Lite anuncia 50 solicitudes mensuales y un equipo; condiciones comerciales y planes integrator corresponden al proveedor, sin contratar ni prometer compatibilidad universal ([precio](https://www.printnode.com/en/pricing), [instalación Windows](https://www.printnode.com/en/docs/installation)). La API documenta X-Idempotency-Key con retención de 24 horas y estado done como entrega a spooler; aun así no se reenvía un envío indeterminado ([API oficial](https://www.printnode.com/en/docs/api/curl)).

Google: OAuth offline/state/refresh y revocación según [OAuth servidor](https://developers.google.com/identity/protocols/oauth2/web-server), PKCE [referencia oficial](https://developers.google.com/identity/protocols/oauth2/native-app). Se solicitan drive.readonly + drive.file: lectura de entradas y creación de salidas, sin escribir fuentes; drive.readonly exige evaluación de scopes restringidos/verificación antes de producción ([scopes](https://developers.google.com/workspace/drive/api/guides/api-specific-auth)). Frontend selecciona/autoriza salida con Google Picker. Cursor changes usa nextPageToken y solo al terminar newStartPageToken ([changes](https://developers.google.com/workspace/drive/api/reference/rest/v3/changes/list)).

Pendiente evidencia externa: OAuth client/consent/scopes verificados, proveedor real, Windows y dos modelos físicos probados, seguridad de cuenta/borrado y TTL, workers OIDC desplegados. Los tests usan proveedores simulados; no afirman instalación ni impresión física.

Delta FE de integración: POST /integrations/drive/connections/:id/picker-token {} (Firebase, flag/owner/revocation recheck) devuelve {accessToken,expiresIn,appId,scopes}; Cache-Control: no-store. Access token efímero emitido por Google, duración real expiresIn (habitualmente una hora), solo en memoria del navegador y jamás logs/localStorage/analytics; refresh token sigue cifrado exclusivamente servidor. Config adicional GOOGLE_DRIVE_PICKER_APP_ID = número del mismo proyecto Cloud; frontend aporta developer API key restringida a su origen y APIs habilitadas, usa setOAuthToken/accessToken, setAppId/appId y vista de carpetas seleccionables. Scopes exactos drive.readonly + drive.file: lectura de nuevos archivos de entrada requiere readonly (seleccionar una carpeta con drive.file no concede todos sus futuros archivos), Picker autoriza carpeta salida para creación. Ausencia de configuración devuelve 503, revocación impide nuevos tokens; token ya entregado conserva la vida que Google determine. [Picker oficial](https://developers.google.com/workspace/drive/picker/guides/web-picker).

Print adicional: GET /print/jobs -> {items:[job]} (máximo 100 propios). Cada job expone stateVersion (alias de version servidor) y clientFreshness=unknown|recent|stale separado de status. Confirm requiere {printed:true,stateVersion}; reprint requiere {confirm:true,stateVersion} y nueva Idempotency-Key; versión antigua devuelve 409 STATE_VERSION_CHANGED, incluyendo carrera entre preflight y transacción. La confirmación manual incrementa stateVersion.

Drive retry delta: GET connections/:id/runs devuelve expiresAt ISO y retryable calculado de failed + conexión activa no revocada + TTL vigente. POST /runs/:id/retry requiere Idempotency-Key; ledger drive_retry_requests ligado cuenta+clave y runId, replay devuelve {id,status,duplicate:true} sin reencolar otra vez aunque el procesamiento haya cambiado de estado; reutilización para otro run devuelve 409. Primer retry válido -> {id,status:"queued",duplicate:false}.

## Persistencia, workers y borrado

| Colección | Retención / propósito |
| --- | --- |
| drive_oauth_states | expiresAt Timestamp, TTL 10 minutos; hash de state, verifier AES-GCM, cuenta; consumo transaccional |
| drive_connections | Sin TTL; refresh cifrado, receta/versiones y cursor; revocar antes de eliminar |
| drive_runs | expiresAt Timestamp, TTL 90 días; identidad conexión+fileId+headRevisionId+recipeVersion, checksum y recibo de salida |
| drive_retry_requests | Mismo expiresAt del run; dedup cuenta+Idempotency-Key, vínculo runId |
| drive_revocations | Sin TTL mientras queued/delivering/failed; acknowledged elimina secreto y añade expiresAt de 7 días |
| print_connections | Sin TTL; key AES-GCM hasta desconexión/borrado; nunca se devuelve |
| print_jobs | expiresAt Timestamp, TTL 90 días; dedup cuenta+Idempotency-Key, source propio, estado/version, ID proveedor, confirmación manual |

Habilitar políticas Firestore TTL sobre expiresAt de las cinco colecciones que lo usan (oauth_states, runs, retry_requests, revocations, print_jobs); no están desplegadas. Consultas de workers usan availableAt/nextScanAt <= now con orderBy del mismo campo e índice simple; consultas cuenta/connectionId usan igualdad; cleanup Drive ordena por __name__ con accountId. Indexación/TTL deben validarse en staging. TTL es limpieza asíncrona: workers comprueban expiración y ownership, no se basan en el borrado automático como autorización. La deduplicación del histórico está acotada a su retención de 90 días.

Root invoca únicamente desde scheduler autenticado OIDC los métodos FolderAutomationService.scanDue(1..50), processDue(1..50), revokePending(1..50) y DirectPrintService.dispatchJobs(1..50), valores por defecto 10. No hay rutas públicas de worker. Scan: hasta 5 páginas de 100 archivos por conexión, cursor+admisión de jobs atómicos, escaneo cada cinco minutos al completar, lease dos minutos y recuperación de cursor 410 mediante nueva enumeración conservando ledger. Procesamiento Drive: lease diez minutos renovado cada 30 segundos, máximo ocho intentos por ciclo, espera un minuto, payload ZPL 1 MiB, máximo 500 etiquetas antes de conversión y 500 páginas PDF después, PDF 10 MiB. OPERATION_IN_PROGRESS reintenta sin consumir intento; ID de conversión/cuota permanece igual. Source ZPL y nombres no van a eventos/logs de estos módulos: el renderer compartido conserva su fuente durable en Storage bajo debug-zpl/{uid}/durable, con política compartida de borrado/retención; el PDF usa el Storage propio existente.

Output Drive obtiene ID antes del upload, guarda checksum, y verifica ID, parent, mimeType, appProperties y MD5 del archivo realmente creado; tras respuesta o commit perdido recupera recibo antes de volver a descargar la revisión. Archivo fuente no se modifica ni mueve; no se descargan URLs suministradas por cliente. Un escaneo vacío, un job aceptado o una conversión sin output Drive confirmado no emite folder_run_succeeded. Estado terminal y outbox canónico se escriben en la misma transacción; fallo de evento evita marcar éxito.

Print: envíos leen exclusivamente PDF completado propio vía StorageService; aceptación y envío vuelven a comprobar impresora en la cuenta de la key. Lease de despacho 60 segundos, timeout proveedor 15 segundos, redirect deshabilitado, host fijo api.printnode.com. Se marca intención antes de la red: crash/timeout/409/429/5xx/ID inválido -> unknown conservador, nunca otro POST automático. Respuesta inequívoca guarda providerJobId, polls solo GET con lease y fencing hasta 120 intentos o un día; errores no autorizan reenvío. new/sent_to_client -> sent, done -> acknowledged (cola SO), error/expired -> failed; sin evidencia -> unknown. Observación del cliente pasa a stale tras dos minutos, sin cambiar resultado del job. Reprint nuevo consume stateVersion del original; repetición exacta misma clave devuelve mismo job, nueva acción con versión antigua 409. print_job_acknowledged y print_confirmed manual son hechos diferentes y atómicos con outbox.

Borrado: poner tombstone antes de barrer datos; invocar `enqueueAccountDriveRevocations(db, accountId)` exportado desde `src/modules/folder-automation/drive-revocation.repository.ts` antes de eliminar drive_connections, y abortar el barrido si falla. No precisa inyectar un módulo ni abre otra conexión Firestore. Copia refresh cifrado a drive_revocations y conserva AAD drive:{accountId}:{connectionId}; luego root puede eliminar conexiones, oauth_states, runs, retry_requests, print_connections, print_jobs por accountId junto con durable_operations/Storage/outbox según contrato compartido. **Excluir drive_revocations de ese barrido**: es la obligación mínima residual de revocación, worker funciona aunque cuenta/conexión hayan sido eliminadas. Revocación tiene lease 60s, backoff 1 minuto hasta 1 hora y máximo ocho intentos; un fallo no impide otros. Failed conserva ciphertext sin TTL y requiere alerta/resolución; `retryDriveRevocation(db,id)` permite reinicio explícito tras corregir causa. Acknowledged quita secreto y añade TTL7d. Si OAuth entrega un token durante la carrera de tombstone, se encola su revocación y no se recrea la conexión. Google puede revocar el grant de la aplicación (afectando otras conexiones del mismo Google user), no se promete revocación independiente de cada carpeta.

Disconnect Drive devuelve conexión safe: disconnected si confirmó proveedor, disconnecting si la revocación está diferida (ambas bloquean trabajo). Disconnect Print elimina key local y devuelve providerKeyRevocation=user_must_revoke_at_printnode: el usuario debe revocar su key en PrintNode; no afirmamos haber revocado credencial externa ni cancelado una impresión ya recibida por el SO. Un efecto externo ya iniciado no se puede deshacer: se preservan recibos y estados honestos; ningún reintento repite un POST de impresión incierto.

Prerrequisitos externos aún sin evidencia: secretos OAuth/encryption, APIs Drive/Picker habilitadas, redirect HTTPS exacto, origen/API key de Picker restringidos, número de proyecto coherente, consentimiento/scopes restringidos y verificación/evaluación de seguridad que Google exija, cuenta/plan PrintNode propia e instalación Windows, conectividad y pruebas físicas con dos modelos de impresora. No se ejecutó llamada real a Google/PrintNode, impresión, despliegue, habilitación TTL ni verificación física.
